# 作用域、存储期与链接

> 定位：把三个经常被混成一个词的东西拆开。**作用域**管"哪行代码能写这个名字"，**存储期**管"这个对象活多久"，**链接**管"别的编译单元能不能看见它"。

## 1. 三个正交维度（先建坐标系）

| 问题 | 维度 | 取值 | 由什么决定 |
|---|---|---|---|
| 这个名字在哪些**源代码位置**有效？ | 作用域 scope | 文件 / 块 / 函数原型 / 函数 / 构造(component) | 声明写在哪 |
| 这个对象**活多久**、放在哪？ | 存储期 storage duration | 静态 / 线程 / 自动 / 分配 | 存储类说明符 + 是否 malloc |
| 这个名字能否**跨 TU** 引用？ | 链接 linkage | 无 / 内部 / 外部 | `static` / `extern` / 是否函数 |

三个维度独立变化的例子，背下来就通了：

```c
static int g;            /* 文件作用域 + 静态存储期 + 内部链接 */
extern int g;            /* 文件作用域 + 静态存储期 + 外部链接（这是声明，不是定义）*/
int g;                   /* 文件作用域 + 静态存储期 + 外部链接 —— ⚠️ tentative definition，见第 6 节 */
void f(void) {
    static int s;        /* 块作用域 + 静态存储期 + 内部链接 —— 活一辈子，别人看不见 */
    int a;               /* 块作用域 + 自动存储期 + 无链接 */
    _Thread_local int t; /* 块作用域 + 线程存储期 + 内部链接（C11）*/
}
```

**`typedef` 与 `#define` 都不产生对象、不产生符号**：`typedef` 名在文件作用域也只是编译期信息，`nm` 里看不到它；`#define` 在预处理后就消失了（`04_Preprocessor_Macro`）。所以"头文件里 typedef 一个结构体被 100 个 .c 包含"不会有任何链接问题。

## 2. 四种名字空间：为什么 `struct stat` 和变量 `stat` 能同名

C 把标识符分成四个互不打架的名字空间（C11 6.2.3）：

```text
1) 标签名        struct/union/enum 的 tag        例：struct Node
2) 成员名        struct/union 成员 + 枚举常量     例：Node.next、RED
3) 普通标识符    变量、函数、typedef、枚举名等     例：int node;、void node(void)
4) 标签名(独立)  goto 的标签                      例：err_out:
```

于是这些全部合法且互不干扰：

```c
struct stat { int st_mode; };        /* 标签名空间 */
extern int stat(const char *, struct stat *);   /* 普通标识符空间：函数也叫 stat */
enum E { member };                   /* member 是枚举常量，在成员名空间 */
int member;                          /* 同名变量：普通标识符空间 —— 合法 */
```

这是 POSIX 系统头能同时有 `struct stat` 与 `stat()` 的原因，也是 `_` 前缀约定的动机：

```c
struct Node { struct Node *next; };   /* 内部提前引用自己：合法，标签已被声明 */
typedef struct Node { ... } Node;     /* ✅ 惯例：tag 在标签空间，Node 在普通空间，两者共存 */
```

**保留标识符**（违反是 UB，不是"风格问题"）：`_` 开头、`__` 开头、以及库函数名形式（如 `malloc`、`printf`）不可自定义；`struct my_malloc` 之类可以，但全局符号请一律避开。

## 3. 作用域与遮蔽（shadowing）

五种作用域：

```text
文件作用域     在任何 {} 之外声明 —— 从声明点到文件尾
块作用域       {} 内 —— 从声明点到该块结束
函数原型作用域 参数名 —— 只在原型内部有效（void f(int x) 里的 x 在定义里可以复用/省略）
函数作用域     标签 —— 整个函数内可见，哪怕定义在块里（所以标签不能重名）
构造作用域     struct/union 成员名 —— 从成员声明到该结构体定义结束（C11 新增，为了匿名成员）
```

遮蔽规则：内层同名即遮盖外层，`int i = i;` 甚至能用自己初始化（取的是外层 `i`，若外层不存在则未初始化读 = UB）。

```c
int x = 1;
void f(void)
{
    int x = 2;            /* 遮蔽全局 x —— 编译无警告，除非开 -Wshadow */
    {
        struct S { int x; } s;   /* 成员 x 在成员名空间，又不冲突 */
        s.x = 3;
    }
}
```

`-Wshadow` 值得常开：多层循环里 `size_t i` 被内层再声明一次，是"下标算错但看起来对"的高频来源。想显式访问被遮蔽的全局量，C 里没有 `::`——只能重命名（前缀化：`g_count`/`m_count`/`ctx->count`），这也是真实项目普遍用命名前缀的原因（见 `12_Generic_Container` 的 API 命名）。

## 4. 存储期：静态 vs 线程 vs 自动 vs 分配

```c
static int a = 5;        /* 常量初始化：编译期定值，进 .data */
static int b;            /* 零初始化：进 .bss（不占文件体积）*/
static const char *s = "hi";   /* 指针指向字面量：初始化是常量表达式，合法 */
static int c = b + 1;    /* ❌ 报错：静态存储期对象只能用常量表达式初始化 */
static int d[] = { 1, 2 };
static int *p = d;       /* ✅ 数组地址是常量表达式，可以 */
static int e[] = { sizeof(d) };  /* ✅ 编译期已知 */
```

三条硬规则：

1. **静态存储期对象只能用常量表达式初始化**（`sizeof`、字面量、地址、`enum` 值）。想要"运行时算出来的初值"只能：`int init(void){ if (!ready) { value = compute(); ready = 1; } }`，或函数内静态懒初始化。
2. **自动存储期对象没有默认初值**：`int a;` 是脏内存，读它 = UB。`= {0}` 只保证第一个元素被显式清零、其余按规则补零 —— 整个数组清零的正确写法是 `int a[10] = {0};`（或 `= {}`，C23）。
3. **静态对象的初始化发生在 `main` 之前**（零/常量初始化由加载器完成），**块作用域 static 的初始化只在第一次可能执行的流过时发生一次**。C 里没有构造/析构函数，收尾靠 `atexit`：

```c
#include <stdlib.h>
static void cleanup(void) { /* 释放全局资源 */ }
int main(void)
{
    if (atexit(cleanup) != 0) { /* 注册失败（C99 至少保证 32 个）*/ }
    ...
    return 0;                  /* 正常返回/exit() 都会跑 cleanup；_Exit()/abort() 不跑 */
}
```

GCC 扩展（MinGW 可用，**待实测**）：`__attribute__((constructor))` / `((destructor))` 让函数在 `main` 前 / 退出时自动跑，DLL 场景里也被 CRT 入口调用。它方便，但**顺序跨 TU 不可控**，只适合"与任何其它初始化无关"的自包含注册（比如把插件挂进全局表）。写库时优先显式 `xxx_init()`：可控、可测、可重入。

`_Thread_local`（C11）/ C23 `thread_local`（`<threads.h>` 提供宏）：每个线程一份副本，块作用域也能用。它属于静态存储期家族（每个线程各一份"静态"），不是自动存储期 —— 与 `17_Concurrency` 交界，本批只记语义。

## 5. 链接规则总表（背这张表就够）

| 声明位置 / 写法 | 链接 | 说明 |
|---|---|---|
| 函数，文件作用域，默认 | 外部 | 所有 TU 可见 |
| `static` 函数 | 内部 | 只在本 TU；别的 TU 可以有一个同名函数，互不干扰 |
| 对象，文件作用域，`extern` 或默认（tentative） | 外部 | 全局符号 |
| 对象，文件作用域，`static` | 内部 | 本 TU 私有数据 |
| 对象，块作用域，`static` / `_Thread_local` | 内部 | 隐藏但长命 |
| 对象/参数，块作用域，`auto`/`register`/默认 | 无 | 每次进入块都是新对象 |
| `typedef` 名、枚举常量、结构体成员、标签、`goto` 标签 | 无 | 不生成任何符号 |
| `#define` | 无（预处理后不存在） | 见 `04_Preprocessor_Macro` |

推论：**"内部链接"是 C 里唯一的私有机制**（没有 access specifier）。设计模块时，凡是没在头文件里承诺的函数与变量，一律 `static`。副作用有三个，全是好事：

- 别的 TU 撞名不会冲突；
- 链接器能删掉未使用的内部函数（`-Wunused-function` 还会提醒你删）；
- 内部链接的函数更容易被内联/特化，优化器不受"可能被外部调用"束缚。

## 6. 声明 vs 定义，以及 `multiple definition` 的真正来源

```c
extern int g_count;      /* 声明：不分配空间，不生成符号 */
int g_count;             /* ⚠️ tentative definition：可能分配空间、可能生成 COMMON 符号 */
int g_count = 0;         /* 定义：确定分配、确定生成符号 */
```

**tentative definition 是 C 独有的坑**（C++ 里没有）：文件作用域写 `int g;` 且没有 `extern`、没有初始化器，它既不是纯声明也不是正式定义。多个 TU 各写一份 `int g;`：

```bat
:: GCC 9 及以前（默认 -fcommon）：合并成一个符号，链接"成功"，两个文件共享同一个 g
:: GCC 10 起（默认 -fno-common）：直接报错误
gcc : multiple definition of `g'; a.o:a.c first defined here ; b.o:b.c ...
```

所以你在这套 GCC 15 上看到的 `multiple definition`，八成就是有人在 `.h` 里写了 `int g_flag;` 而 `.h` 被两个 `.c` 包含。**这是好消息**：C 标准本来就不保证那种合并，老 `-fcommon` 让两个模块"意外共享同一变量"是典型隐蔽 bug（`-fno-common` 是当年为修 Linux 内核这类问题改的默认值）。

**唯一正确模式**（背下来）：

```c
/* counter.h —— 只声明 */
#ifndef COUNTER_H
#define COUNTER_H
extern int g_counter;              /* ✅ extern 声明，无初始化器 */
void counter_reset(void);
#endif

/* counter.c —— 定义一次 */
#include "counter.h"
int g_counter = 0;                 /* ✅ 定义：全程序恰好一处 */
void counter_reset(void) { g_counter = 0; }
```

**数组的 extern 写法**（一写错就静默出鬼）：

```c
/* counter.c */
int g_tab[10];

/* ❌ 错误声明：类型是 int*，与 int[10] 的对象不兼容。链接能过（符号名匹配），
      但 g_tab2 读出的是数组前 8 个字节当作指针值 —— 典型的"能编译能链接，运行时乱码" */
extern int *g_tab2;

/* ✅ 正确：声明为不完整数组类型，编译器知道它是数组 */
extern int g_tab[];
/* 附赠检测手段：在其它 TU 里 sizeof g_tab 会直接编译报错（对不完整类型求大小），
   而 extern int *g_tab 的 sizeof 是 8 —— 不报错，静静骗你 */
```

`extern` 的另一个冷知识：**在函数体里写 `extern int g;` 会引入一个外部链接的名字**，之后的 `g` 指向全局那个，而不是新局部变量。别在块里写 extern。

## 7. `inline`：三种流派，写错就 `undefined reference`

C99 的 `inline` 与直觉完全不同，它**只是给编译器的提示 + 改变"这份定义算不算定义"**。三种写法的后果：

| 写法 | 链接 | 是否在**本** TU 留下外部定义 | 头文件里能写吗 |
|---|---|---|---|
| `static inline int f(void)` | 内部 | 每个包含它的 TU 各得一份（未用则删） | ✅ **推荐**，最安全 |
| `inline int f(void)`（C99 语义） | 外部 | ❌ **不生成**！必须有某个 TU 写 `extern inline` | ⚠️ 需要配套，否则 `undefined reference` |
| `extern inline int f(void)`（C99 语义） | 外部 | ✅ 生成外部定义（恰好一个 TU 写） | ❌ 只能出现在一个 .c |
| `extern inline int f(void)`（**GNU 模式**，`-std=gnu*`） | 外部 | ❌ 不生成（等价于 C99 的第二行！） | ⚠️ 语义与上面**正好相反** |

关键：**`-std=c99/c11/c17/c23` 与 `-std=gnu*` 下 `extern inline` 的含义相反**（GNU 流派是历史遗留）。GCC 15 默认是 `gnu23`，于是从"C99 教科书"抄来的代码会在链接期缺符号。**本仓库统一 `-std=c11`，并且规则简化成一条**：

```c
/* 头文件里的工具函数：一律 static inline */
static inline int clamp_int(int v, int lo, int hi)
{
    return v < lo ? lo : (v > hi ? hi : v);
}
/* 唯一代价：每个包含它的 .c 都可能得到一份代码（未用会被丢弃），
   以及不能拿它的地址跨 TU 比较（&f 在不同 .c 里可能是不同地址）。 */
```

其它平台的坑：**MSVC 的 C 模式不支持 C99 `inline` 语义**（`inline` 当作 `static inline` 处理），所以依赖 C99 `extern inline` 的代码在 MSVC 上直接不兼容。写可移植库时把 `static inline` 当唯一手段，或自己包一层宏（`15_Build_Library` 会处理导出宏）。

## 8. 全局状态的正确写法（按优先级）

```c
/* 方案 1（最好）：根本没有全局 —— 状态放进结构体，由调用方持有 */
typedef struct Ctx { int count; } Ctx;
void ctx_tick(Ctx *c) { c->count++; }

/* 方案 2：模块私有状态 + 访问函数（把"内部链接"当封装用） */
/* counter.c */
static int s_count;                 /* 内部链接：外面看不见的模块状态 */
int  counter_get(void)  { return s_count; }
void counter_add(int n) { s_count += n; }
/* counter.h */
int  counter_get(void);
void counter_add(int n);
/* 好处：可以加断言/日志/未来换成线程局部，而调用方代码不动 */

/* 方案 3：单例句柄（需要跨模块共享一个状态机时用） */
/* app.h —— 前向声明：调用方只知道"有 struct App 这种东西"，不知道它的布局 */
struct App;
struct App *app_get(void);
/* app.c —— 完整定义只出现在这里，成员怎么改都不影响调用方（信息隐藏/ABI 稳定）*/
struct App { int running; /* ... */ };
static struct App g_app = { .running = 1 };   /* 变量本身内部链接 */
struct App *app_get(void) { return &g_app; }  /* 只暴露指针，不暴露定义 */

/* 方案 4（应避免）：裸全局变量 extern int g_flag; 到处读写
      问题：数据竞争（UB）、无法测试（无法重置）、初始化顺序无保证、跨平台命名冲突 */
```

**"头文件里写函数定义"这件事**：因为 `#include` 是文本复制，一个 .h 被 N 个 .c 包含，`void f(void){}` 就会变成 N 份外部定义 → `multiple definition`。所以头文件里只放：声明、宏、typedef、`static inline` 函数、`extern` 数组/变量声明。这条纪律也是 `04_Preprocessor_Macro` 里 include guard 存在的理由。

## 9. 先弄清"编译单元（TU）"到底是什么

```text
一个 .c 文件 + 它所有 #include 展开的结果 = 一个翻译单元（translation unit）
GCC 一次 gcc 调用编一个 .c → 一个 .o（目标文件）
链接器把所有 .o（+库）合起来 → .exe / .dll
```

所以：

- `static` 的边界是 **`.o`**，不是"项目"，也不是"文件夹"。`a.c` 和 `b.c` 各写一个 `static int x;` → 两个毫无关系的变量。
- 头文件里写 `static int cfg = 1;` → **每个包含它的 .c 各得一份副本**，改一份不影响另一份。这是"为什么我改了全局值没生效"的经典答案之一。
- 一个符号在链接期才决定归属：`gcc a.c b.c -o app` 是一条命令两步做（各自编译 + 链接），报错信息里的 `a.o:b.c` 就是告诉你"这个定义来自哪个文件"。

## 10. 用符号表把链接问题看穿（Windows/PE 注意点）

```bat
gcc -std=c11 -c a.c -o output\a.o          :: -c：只编译不链接
gcc output\a.o output\b.o -o output\app.exe
nm output\a.o                              :: 看这个 TU 产生了什么、需要什么
objdump -t output\a.o                       :: 另一种视图（带 section 名）
objdump -T output\some.dll                  :: ELF 风格动态符号；MinGW 生成的 DLL 常常要用
objdump -p output\some.dll | findstr /i "ordinal name"   :: PE 导出表
```

`nm` 的字母含义（ELF 习惯，PE 下大致对应，**本机输出格式待实测**）：

```text
大写 = 外部链接（全局），小写 = 内部链接（static）
T/t  代码段 .text         D  已初始化数据 .data      d  局部已初始化数据
B/b  未初始化数据 .bss     R/r 只读数据 .rodata
W    弱符号               U  未定义（需要链接期从别处补，正是 undefined reference 的来源）
A    绝对值（常见于 32 位 Windows 的段基址，忽略即可）
```

Windows/MinGW 特有的三条：

1. **32 位目标符号带前导下划线**（`_main`），64 位不带。写 `.def` 文件、手搓 `__declspec`、或从 C++ 里按名字查符号时会撞上。
2. **`-fvisibility=hidden` 在 PE/COFF 上没有 ELF 的符号隐藏效果**。Windows 上的可见性由 `__declspec(dllexport/dllimport)` 决定，别指望 `-fvisibility` 帮你藏内部符号（`15_Build_Library` 的导出宏专门处理这个差异）。
3. **`static` 函数在 DLL 里当然也不导出**，与 ELF 一致；想导出就必须外部链接 + `dllexport`。

顺带一个真实工程结论：**给内部函数一律加 `static`，`nm` 的输出会明显变干净**，排查"符号哪来的"时少一半噪音。

## 11. 两类链接错误的排查流程

**A. `undefined reference to 'foo'`**

```text
1) 名字对不对？ —— C++ 会 mangling，看错误里是不是 _Z3fooi 这种。是 → 缺 extern "C"（见 15）
2) 定义存在吗？ —— nm 每个 .o 找 T/t 里的 foo；都没有 → 你压根没写实现
3) 存在但没链接进来？ —— 检查：
     · gcc 顺序：调用者在左？库在右？（静态库只被扫描一次）  gcc main.o -L. -lfoo  ✅
     · 库文件名：libfoo.a / foo.dll / foo.lib —— MinGW 用 -lfoo 匹配 libfoo.a 或 libfoo.dll.a
     · 函数被 #ifdef 编掉了？（gcc -E 看看，或 nm 看该 .o 里是不是根本没这符号）
     · 声明成 static 而在别的 TU 用？（那是 internal linkage，外部看不见）
4) 库存在但架构/ABI 不符？ —— objdump -f 看文件是 pe-x86-64 还是 elf64-x86-64；32/64 混链接是典型事故
```

**B. `multiple definition of 'foo'`**

```text
1) 头文件里写了定义？  → 改成声明 + 恰好一个 .c 里定义（第 6 节）
2) 两个 .c 定义了同名外部函数？ → 其中一个应加 static
3) tentative definition 撞车？（int g; 出现在多个 TU）→ 头文件用 extern int g;
4) 同一个 .c 被编了两次？（build 脚本同时写了 src/a.c 与 glob 展开的 a.c）→ 检查源列表
5) 临时验证手段：gcc -fcommon ... 让它"回到旧行为"，只为确认根因，别提交
```

## 12. 陷阱清单

```c
/* 1. 头文件里定义变量/函数 → N 份定义（第 6/8 节）*/
/* 2. extern int *arr; 配 int arr[N]; → 链接通过，运行乱码（第 6 节）*/
/* 3. 块作用域 static 当成"每次重置"用：
      void f(void){ static int n = 0; n++; }   → n 只初始化一次，第二次调用返回 2 */
/* 4. 块作用域 static 的初始化在多线程首次调用时不是原子的（C 不保证），别当线程安全的懒加载
      → 需要时换成显式 init 或 _Atomic 状态位（17_Concurrency）*/
/* 5. 忘记 static → 工具函数变成全局符号，与第三方库同名而"链接到了别人的实现"（真实事故高发区）*/
/* 6. 用 sizeof 判断 extern 数组长度 → extern int a[] 会报错，extern int *a 会静默给 8（第 6 节）*/
/* 7. 依赖"全局变量在 main 前被某个 .c 的语句初始化" → C 没有这种初始化顺序，必须显式 init() */
/* 8. atexit 里访问已经退出的全局（尤其 DLL 卸载路径）→ 只做幂等、无依赖的收尾 */
/* 9. typedef 结构体同名 tag：typedef struct S S; 之后 struct S{...} 才定义 → 前向声明标准手法，
      用来在头文件里隐藏布局（第 8 节方案 3）*/
/* 10. 在 .c 里用 extern 声明一个"其实是函数"的名字，或反过来 → 链接期符号类型不匹配 */
```
